# 야간 TO 전력 입력 — 항목별 부분 저장, 2026-10-19

## 화면과 입력
보직현황의 선택 근무가 N/S이고 **로그인 계정의 직원 정보 `employees.position`이 `TO`**일 때 TO 카드 오른쪽 위에 [전력 입력]을 표시한다. TO 업무일지를 아직 작성·임시저장하지 않았어도 버튼을 사용할 수 있다. 일반/관리자/최고관리자 같은 계정 권한은 우회 조건으로 사용하지 않고, 실제 등록 보직이 TO인지 여부만 본다. 직원 정보에서 로그인 허용이 해제되거나 보직이 TO가 아니면 입력·수정 권한을 주지 않는다.

발전량·수전량·송전량·태양광 발전량 네 항목은 모두 kWh로 입력한다. 한 항목 이상 입력하면 저장할 수 있다. 신규 빈칸은 null(미입력)이며 실제 0은 유효한 입력값이다. 이후 미입력 항목을 추가할 수 있다. 기존 숫자를 입력창에서 직접 지우고 저장하면 해당 항목을 미입력으로 변경할 수 있다. 네 칸이 모두 비어 있는 요청은 저장하지 않는다. 기준일은 선택한 야간 근무 시작일이다. 예: 9월 26일 N/S 담당자가 27일 새벽에 입력하는 실적은 26일 자료이다.

API의 GET/POST 성공 응답에는 `capabilities: {partialValues: true, clearFields: true}`를 포함한다. 업데이트된 입력창은 기존 숫자(0 포함)를 직접 지운 항목만 선택적 `clearFields` 배열에 명시한다. 배열은 중복 없는 정식 항목명이어야 하며 해당 `values` 값은 반드시 null이어야 한다. 과거 클라이언트의 null 요청은 기존과 같이 저장된 숫자를 보존한다. 이미 미입력인 항목을 명시적으로 비우는 요청은 같은 null로 유지한다. 미입력 변경도 TO 권한·최신 revision·원자적 저장·변경 이력을 모두 적용한다. 서버가 명시적 비우기를 지원한다고 응답하지 않으면 입력창은 요청을 보내지 않고 배포/새로고침 안내를 표시한다.

## 기존 일지 동기화와 전력 저장의 분리
- 전력 원본은 `to_night_power_daily`에 실적 기준일을 기본키로 저장한다. 변경 이력은 `to_night_power_audit`에 별도 저장한다. 업무일지의 본문·log_json·legacy 원본·OIS 결과에 넣지 않는다.
- 전력 입력 권한은 업무일지 ID·작성자·revision과 분리한다. 브라우저의 기존 계약 호환을 위해 `sourceLog` 모양의 권한 토큰을 사용하지만 값은 `employee-position:<사번>`이며 실제 업무일지를 가리키지 않는다.
- 기존 일지에 전력 항목이 없거나 빈칸/null/0으로 들어와도 전력 수정 요청으로 취급하지 않는다. 기존 일지 동기화·ID 재생성·본문 교체는 전력 저장값이나 변경 이력을 갱신하지 않는다.
- 조회와 동기화에서 전력 POST를 하지 않는다. 네 항목의 숫자/null과 최신 revision을 검증한 명시적 저장 요청만 전력 값을 변경한다. null은 기본적으로 기존 항목을 유지하고 새 항목에는 미입력으로 저장한다. 사용자가 직접 지운 항목을 `clearFields`로 명시했을 때에만 해당 기존 숫자를 null로 바꾼다. 기존 0을 자동으로 지우거나 과거 자료를 일괄 수정하지 않는다. 전체 기록 삭제 API는 제공하지 않는다.

## 오전회의 전력 현황
같은 날짜의 TO 저장값을 오전회의 전력 현황과 최종 엑셀에 우선 반영한다. 일부 저장 시 `TO 일부 입력 3/4`처럼 표시하고, 입력한 숫자만 나타낸다. 미입력 항목은 카드에서 `-`, 엑셀에서 빈칸이며 과거 자료로 채우거나 0으로 바꾸지 않는다. 네 항목이 모두 입력된 경우에만 입력 완료로 표시한다.

- 발전량 → TO `generatorEcmsGen1`
- 수전량 → TO `ismartReception`
- 송전량 → TO `epowerTransmission`
- 태양광 발전량 → TO `solarDailyGeneration`
- 태양광 월간 누적 → TO 일일 태양광을 우선하여 서버에서 파생 계산
- 태양광 년간 누적 → TO 일일 태양광을 우선하여 서버에서 파생 계산

TO 저장 성공 직후 오전회의 카드가 다시 그려지며, 다른 화면에서 오전회의를 열거나 새로고침할 때도 서버에서 최신 TO 저장값을 다시 조회한다. 전력 GET은 Excel/Agent/DataPARC 조회를 시작하지 않는다.

## 태양광 월간·년간 누적
누적값은 TO 입력 테이블에 별도 저장하지 않고 **조회 시 서버에서 파생 계산**한다. 따라서 과거 날짜의 TO 태양광 발전량을 수정하면 이후 날짜를 조회할 때 최신 입력을 기준으로 누적값이 다시 계산된다.

월간 누적은 달의 1일부터 시작한다. 예를 들어 9월 30일 월간 누적이 얼마였든 **10월 1일 월간 누적은 10월 1일 태양광 발전량부터 새로 시작**한다. 년간 누적은 월이 바뀌어도 이어지며, 1월 1일에 해당 연도의 일일 발전량부터 새로 시작한다.

기능 도입 이전 기간은 기존 `morning_meeting_auto_history_overrides`의 태양광 일일/누적 기록을 **읽기 전용 기준값**으로 사용한다. TO가 입력한 날짜는 TO 일일값을 우선한다. 발전량·수전량·송전량의 빈칸은 입력된 태양광 발전량의 누적 계산을 막지 않는다. 해당 날짜의 태양광 발전량 자체가 미입력이거나 사용자가 명시적으로 비운 경우 그 날짜의 일일·월간·년간 표시는 미입력으로 유지한다. 연속 계산에 필요한 기준값이나 중간 일일값을 안전하게 확인할 수 없는 경우에도 누적을 임의의 0으로 만들지 않고 null로 반환한다. 기존 자동수치 기록을 수정하거나 마이그레이션하지 않는다.

## 브라우저 보호와 최종 엑셀
같은 로그인 세션·같은 날짜에서 확인된 전력 저장값은 재조회 중에도 표시한다. 조회가 실패하면 `재조회 실패 · 마지막 저장값 유지`로 표시하고 값 자체를 빈칸/0으로 바꾸지 않는다. 한 번 확인된 일일 기록에 대해 이후 GET이 null, 이전 revision 또는 같은 revision의 다른 일일값을 반환하면 마지막 확인값을 유지한다.

태양광 누적은 파생값이므로 같은 일일 기록 revision이어도 과거 날짜가 수정되면 변경될 수 있다. 이 경우 최신 GET의 누적값만 갱신한다. 날짜나 로그인 계정이 다르면 보존값을 섞지 않는다.

최종 엑셀은 선택일의 이미 불러온 저장값을 사용한다. 신뢰할 수 있는 TO 누적값이 있으면 입력된 일일 전력 항목과 함께 월간·년간 태양광 누적을 사용한다. TO 태양광 자체가 미입력이거나 명시적으로 비워진 경우에는 예전 일일·누적값으로 되채우지 않고 해당 셀을 빈칸으로 유지한다. 발전·송전·수전의 기존 kWh→MWh 변환, 태양광 kWh 단위, 증기·혼소·수식은 그대로 유지한다.

## 저장·배포
DB 스키마는 R4와 동일하다. 기존 전력 데이터를 옮기거나 삭제하거나 누적 컬럼을 추가하는 마이그레이션은 없다. 최초 허가된 전력 저장에서 기존 두 TO 전력 테이블만 `CREATE TABLE IF NOT EXISTS`로 만든다. 누적 계산은 TO 전력 테이블과 기존 오전회의 자동수치 기록을 읽기만 한다.

부분 저장 적용기는 최신 main의 별도 Git worktree에 TO API·브라우저 provider·오전회의 저장/엑셀 연동·회귀 테스트·문서·JS 캐시 키를 적용한다. 충돌 시 중단하며, 관련 테스트와 실제 웹 빌드를 통과한 변경만 커밋·일반 push한다. 기존 작업 폴더와 Agent 파일은 변경하지 않는다.

## 검증 범위
Node 실제 SQLite 모의 D1에서 기존 R4 보존/권한 테스트와 함께 다음을 검증한다: 전일 역사 누적 기준 연결, 10월 1일 월간 리셋, 년간 계속 누적, TO 미입력 중간일의 기존 일일값 사용, 기존 목표 누적 보정 fallback, 과거 TO 값 수정 후 이후 누적 재계산, 기준값 부족 시 0 조작 금지, GET의 read-only 보장, 오전회의/최종 엑셀 merge.

실제 운영 Cloudflare D1 종단간 시험은 사용자 PC의 적용 후 배포 화면에서 확인한다. 적용기는 실제 최신 저장소에서 TO 전용 테스트와 웹 빌드를 다시 통과해야만 커밋·push한다.
