# 야간 TO 전력 입력 V1 R4 — TO 보직 계정 권한 + 동기화 보존, 2026-09-27

## 화면과 입력
보직현황의 선택 근무가 N/S이고 **로그인 계정의 직원 정보 `employees.position`이 `TO`**일 때 TO 카드 오른쪽 위에 [전력 입력]을 표시한다. TO 업무일지를 아직 작성·임시저장하지 않았어도 버튼을 사용할 수 있다. 일반/관리자/최고관리자 같은 계정 권한은 우회 조건으로 사용하지 않고, 실제 등록 보직이 TO인지 여부만 본다. 직원 정보에서 로그인 허용이 해제되거나 보직이 TO가 아니면 입력·수정 권한을 주지 않는다.

발전량·수전량·송전량·태양광 발전량 네 항목은 모두 kWh로 입력한다. 빈칸은 미입력이고 실제 0은 유효하다. 기준일은 선택한 야간 근무 시작일이다. 예: 9월 26일 N/S 담당자가 27일 새벽에 입력하는 실적은 26일 자료이다.

## 기존 일지 동기화와 전력 저장의 분리
- 전력 원본은 `to_night_power_daily`에 실적 기준일을 기본키로 저장한다. 변경 이력은 `to_night_power_audit`에 별도 저장한다. 업무일지의 본문·log_json·legacy 원본·OIS 결과에 넣지 않는다.
- 전력 입력 권한은 업무일지 ID·작성자·revision과 분리한다. 브라우저의 기존 계약 호환을 위해 `sourceLog` 모양의 권한 토큰을 사용하지만 값은 `employee-position:<사번>`이며 실제 업무일지를 가리키지 않는다. 전력 자료의 기본키는 날짜이고 업무일지 외래키나 연쇄 삭제 규칙이 없다.
- 기존 일지에 전력 항목이 없거나 빈칸/null/0으로 들어와도 그것을 전력 수정 요청으로 취급하지 않는다. 기존 일지의 덮어쓰기·ID 재생성·본문 교체는 전력 저장값이나 입력자/저장시각/변경이력을 갱신하지 않는다.
- 조회와 동기화에서 전력 POST를 하지 않는다. 네 입력값과 최신 revision을 검증한 명시적 저장 요청만 전력 값을 변경한다. 삭제 API는 제공하지 않는다.
- 동기화로 TO 업무일지 작성자·ID·revision이 달라지거나 일지가 일시적으로 없어져도 저장된 날짜의 전력 값과 TO 보직 계정의 입력 권한은 유지된다. 보직이 변경되면 다음 GET/저장 시 즉시 권한을 다시 확인한다.

## R2 브라우저 보호
같은 로그인 세션·같은 날짜에서 확인된 전력 저장값은 재조회 중에도 표시한다. 조회가 실패하면 `재조회 실패 · 마지막 저장값 유지`로 표시하고 값 자체를 빈칸/0으로 바꾸지 않는다. 한 번 확인된 기록에 대해 이후 GET이 null, 이전 revision 또는 같은 revision의 다른 값을 반환하면 정상 갱신으로 처리하지 않는다. 마지막 확인값을 유지하고 오류 상태로 둔다. 새 revision의 정상적인 수정값은 0이라도 받아들인다.

날짜나 로그인 계정이 다르면 이 보존값을 섞어 쓰지 않는다. 로그아웃·세션 변경 또는 GET에서 인증 거절을 받으면 해당 세션의 보존 표시를 제거한다. 화면에 값을 보존한다고 해서 서버 동기화가 성공했다고 표시하지 않는다. 자동 재시도 루프를 만들지 않는다.

전력 입력창에 타이핑 중인 값은 백그라운드 동기화로 다시 채우지 않는다. 업무일지 revision 변경은 전력 저장을 차단하지 않는다. 다만 저장 직전에 로그인 세션·직원 로그인 허용·TO 보직·전력 revision을 다시 확인하며, 보직 또는 전력 revision이 바뀌었다면 입력 중인 값은 유지한 채 저장을 차단한다. 사용자가 명시적으로 저장자료 다시 불러오기를 선택한 때에만 입력창을 서버 값으로 교체한다.

## 오전회의·엑셀
같은 날짜의 수동 저장값을 오전회의 전력 카드와 최종 엑셀에 우선 반영한다. 아직 수동 입력한 적이 없는 날짜는 기존 조회값을 사용할 수 있다. 전력 GET 조회는 Excel/Agent/DataPARC 작업을 시작하지 않는다.

최종 엑셀은 생성 전에 서버 값을 새로 확인해야 한다. 화면에 남겨 둔 재조회 실패 값은 검증 완료값으로 취급하지 않는다. 최신 값을 확인할 수 없으면 생성 단계에서 오류로 중단하며, 빈칸/자동 0/과거 조회값으로 조용히 대체하지 않는다. 발전·송전·수전의 기존 kWh→MWh 변환 및 태양광 일일 kWh 단위는 유지한다. 증기·혼소·태양광 누적·수식은 변경하지 않는다.

오전회의의 **명시적인 선택일 초기화**는 기존 동작을 유지한다. 초기화가 활성화된 동안 TO 값의 화면/엑셀 재표시도 억제하지만 별도 전력 원본과 이력은 삭제하지 않는다. 이는 일반 [동기화]나 [재조회]와 다른 동작이다.

## 저장·배포
DB 스키마는 기존 R2와 동일하다. 기존 전력 데이터를 옮기거나 삭제하거나 초기값을 채우는 마이그레이션은 없다. 최초 허가된 전력 저장에서 필요한 두 테이블을 `CREATE TABLE IF NOT EXISTS`로 만든다. GET은 테이블을 만들지 않는 조회 전용이다. 전력 원본과 이력은 같은 D1 batch 안에서 갱신하며 세션·직원 로그인 허용·TO 보직·전력 revision을 재검증한다. 기존 `source_log_id/source_log_revision` 컬럼은 스키마 호환을 위해 유지하되 새 저장에서는 계정 보직 권한 토큰을 기록한다.

`apply-to-night-power-v1-r4.cjs`는 R3가 적용된 최신 main에서 API·회귀 테스트·문서만 갱신한다. 브라우저 JS/CSS와 캐시 키는 변경하지 않는다. 대상 파일에 알 수 없는 수정이 있으면 덮어쓰지 않고 중단한다. 백업, 별도 Git worktree의 테스트와 실제 프로젝트 웹 빌드 후 기능 변경만 커밋·일반 push한다. reset/stash/강제 push는 하지 않는다.

## 검증 범위
Node 실제 SQLite에 D1 모의 어댑터를 연결한 API 검증과, V15 R1 script.js의 실제 연동 함수를 발췌한 테스트를 수행한다. 동기화는 기존 일지 테이블을 반복 갱신·재생성·삭제하는 SQL 및 브라우저 상태 갱신으로 재현하며, 이 변경들이 TO 보직 권한과 전력 저장값에 영향을 주지 않는지 확인한다. Chromium 검증은 실제 신규 모듈과 모의 API를 사용한다. 적용기 검증의 Git 원격 저장소와 웹 빌드는 로컬 테스트용이다.

실제 운영 계정·Cloudflare D1·구 업무일지 서버에 접속한 종단간 동기화 시험은 하지 않았다. 실제 프로젝트의 최신 소스 검사와 웹 빌드는 사용자 PC에서 적용 명령을 실행할 때 수행한다. 자세한 결과와 횟수는 패키지의 VERIFICATION.json을 확인한다.
