# 구조 정리 V14 — 업무일지 검색 결과 기능 분리

최종 검증 기준: `78e85b34096db5145f02a8da6a52806402847ebe`.
최초 분석 기준 `719c06e` 이후 Soot Blower API 수정과 추가 검사가 반영됐으며, 해당 변경을 보존한 최신 코드에서 다시 검증합니다.

## 목적과 이번 범위

V12의 구버전·중복 선언 정리와 V13의 전체 회귀 검사 정상화에 이어, 큰 메인 JavaScript의 기능별 분리를 시작합니다. 첫 대상으로 업무일지 검색 결과에서 검색어와 일치하는 업무 항목만 선택하고 강조하는 기능을 분리했습니다.

- `maintenance/shift-log-search-matched-items.js`: 기존 검색 결과 설치 함수 전체를 보존해 옮겼습니다.
- `script.js`: 원래 함수 실행 위치에 `GSShiftLogSearchMatchedItems.install` 호출을 남겼습니다.
- `index.html`: 새 파일을 메인보다 먼저 `defer`로 읽고, 메인 스크립트의 캐시 버전만 갱신했습니다. 기존 석회석 버전 매개변수는 유지했습니다.
- 관련 검사와 이 문서를 추가·갱신했습니다.

검색 조건, 계산식, 화면 문구, 디자인, CSS, 모바일 runtime, Agent/Excel, API와 DB는 변경하지 않았습니다. 검색어가 없는 일반 조회는 기존 검색 함수를 사용합니다. 검색어가 있으면 업무 항목의 분류·시각·TAG·내용·비고에서 찾고 운전현황·작성자 등은 기존 규칙대로 별도 조건으로 처리합니다.

## 실행 순서를 보존한 방법

별도 파일을 메인 다음에 읽어 바로 실행하면, 두 스크립트 사이에서 메인이 예약한 Promise 콜백이 먼저 실행될 수 있습니다. 이를 피하기 위해 새 파일은 **설치 함수만 정의**합니다. 메인 코드가 원래 검색 기능을 설치하던 위치에서 `(0, window.GSShiftLogSearchMatchedItems.install)();`로 호출합니다.

엄격 모드, 기존 함수 3개의 캡처 시점, 전역 lexical 변수 접근, `this` 값 및 Promise 콜백에 대한 실행 순서를 유지합니다. 원래 검색 설치 함수는 21,113바이트이며 분리 전후 함수 바이트와 구문 트리가 같습니다. 나머지 메인 코드의 바이트와 1,143개 최상위 구문도 동일합니다. 새 이름은 기존 코드에 없음을 확인했습니다.

| 의존 대상 | 사용하는 시점 | 용도 |
| --- | --- | --- |
| `createSearchLogText` | 기존 위치의 설치 호출 | 원래 검색 문자열 함수 보존 및 확장 |
| `createSearchLogPreviewHtml` | 기존 위치의 설치 호출 | 원래 미리보기 보존 및 일치 항목 표시 |
| `createSearchLogPreviewText` | 설치 호출 시 존재할 경우 | 기존 선택적 텍스트 요약 확장 |
| `elements.searchForm` | 검색 실행 | 검색어·분류 값 읽기 |
| `collectLogEntriesForDisplay` | 검색 실행 시 존재할 경우 | 기존 업무 항목 정규화 우선 사용 |
| `getSearchEntryCategoryValue` | 검색 실행 시 존재할 경우 | 기존 분류 판정 우선 사용 |

분리 파일은 classic script이며 ES module로 바꾸지 않습니다. 이미 존재하는 전역 변수와의 경계를 한 번에 바꾸지 않고, 먼저 파일과 실행 위치를 분리한 단계입니다. 이 변경만으로 초기 다운로드 크기나 혼소율 계산 시간이 줄었다고 주장하지 않습니다.

## 검사

새 동작 검사는 다음을 다룹니다.

1. 메인 전역 변수보다 먼저 파일을 읽어도 설치는 원래 호출 위치에서만 실행됨.
2. 메인 초기화에서 예약한 Promise보다 먼저 검색 확장이 설치됨.
3. 메인이 원래 호출 위치에 도달하지 못하면 검색 확장을 따로 실행하지 않음.
4. 빈 검색어에서는 기존 조회·HTML·텍스트 요약으로 전달됨.
5. 검색 결과는 일치 항목만 표시하고 전체 업무일지 원본을 바꾸지 않음.
6. 분류·TAG 검색, 불일치 안내, 과거 자료, 비고 및 중복 ID 처리가 유지됨.
7. 기존 정규화 함수와 FormData가 실패하거나 없을 때의 대체 경로가 유지됨.
8. HTML·TAG 속성 이스케이프, 검색어 강조 및 줄바꿈이 유지됨.
9. 다시 로딩·호출해도 기존 중복 설치 방지가 유지됨.
10. 새 파일의 단일 로딩·순서·defer·캐시 버전·공개 빌드 포함을 검증함.

전체 검사와 빌드, 설치·원복·반영 검증 결과는 배포 패키지의 `VERIFICATION.json` 및 `evidence/`를 참조합니다. 자동 검사는 운영 DB/API 또는 회사 PC의 Excel/DataPARC를 호출하지 않습니다. 실제 PC 브라우저 화면과 네트워크 상태까지 검증한 것은 아닙니다.

## 적용과 기존 변경 보존

설치기는 모든 대상과 파일 무결성을 먼저 확인합니다. 알 수 없는 대상 변경은 덮어쓰지 않습니다. 메인 HTML은 새 스크립트 삽입과 메인 캐시 URL만 국소 변경해 다른 화면 작업을 보존합니다. 변경 전 파일을 백업하며, 원복 시에는 이후 추가 변경이 있는지 확인합니다.

전체 검사와 공개 웹 빌드가 통과한 뒤에만 검토한 대상 파일을 커밋·푸시합니다. 관련 없는 working/staged 변경은 보존합니다. 기존 Agent 설정이나 실행 중인 프로세스는 수정하지 않습니다.
